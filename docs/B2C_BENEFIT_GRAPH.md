# B2C 미니앱: 나의 잠재 혜택 찾기 (Benefit Knowledge Map)

> 상태: 제품 브리프 v0. 구현 전, 후보 주제 검토 단계입니다.
> 호스트 앱(규모 있는 슈퍼앱) 안에 미니앱으로 들어가는 것을 전제로 씁니다.

## 0. 한 줄 정의

**내 조건에서 받을 수 있는 혜택을 찾고, 서로 부딪히는 혜택을 걸러, 마지막에 "무엇을 먼저 신청할지" 순서로 정리해 주는 미니앱.**

- 결과물은 목록이 아니라 **결정**입니다. 무엇을 먼저 신청하고, 무엇을 포기하고, 그래서 얼마가 남는지.
- 호스트 앱이 이미 가진 프로필(나이·거주지·소득구간·카드 사용내역)을 그대로 씁니다. 입력 화면을 새로 만드는 순간 미니앱의 강점이 사라집니다.

## 1. 이 주제에 대한 판단

좋은 주제입니다. 다만 "추론"이라고 부르는 부분을 셋으로 쪼개야 제품이 됩니다.

| 단계           | 실제로 하는 일                                       | 필요한 것                        | 흔한 착각                |
| -------------- | ---------------------------------------------------- | -------------------------------- | ------------------------ |
| 1. 자격 판정   | 내 조건이 요건을 만족하는가                          | 룰 엔진(수치 비교, 가구 정의)    | 그래프 추론으로 해결된다 |
| 2. 충돌 감지   | A와 B를 같이 받을 수 있는가. A를 받으면 B가 끊기는가 | 그래프(배타·대체·선후·소득 산입) | 목록만 잘 뽑으면 된다    |
| 3. 조합 최적화 | 어떤 조합이 가장 이득인가                            | 제약 최적화(소규모 완전탐색/ILP) | 그래프 탐색으로 해결된다 |

그래프가 진짜 값을 하는 곳은 2번입니다. 1번은 그래프 없이도 되고, 3번은 그래프로 안 됩니다. 셋을 뭉쳐서 "온톨로지로 다 된다"고 팔면 데모는 되지만 정확도에서 무너집니다. 온톨로지는 후보를 찾고 충돌을 증명하는 데 쓰고, 금액 계산은 코드로 빼는 쪽이 맞습니다.

경쟁도 이미 셉니다. 복지로 맞춤형 서비스, 보조금24, 정부24가 1번을 무료로 합니다. 카드 추천은 뱅크샐러드·카드고릴라가 합니다. 이길 수 있는 지점은 **제도 사이의 충돌**입니다. 지원금을 받아 소득이 잡히면서 건강보험 피부양자 자격이 날아가고, 그 보험료가 지원금보다 큰 경우는 어느 서비스도 미리 알려주지 않습니다.

가장 큰 위험은 기능이 아니라 **오탐**입니다. "받을 수 있습니다"라고 했다가 실제로 안 되면 신뢰가 한 번에 끝납니다. 반대로 못 찾으면 그냥 목록형 서비스와 다를 게 없습니다. 이 둘 사이의 선을 제품 원칙으로 먼저 정해야 합니다.

## 2. 타깃과 문제

| 항목                    | 내용                                                               |
| ----------------------- | ------------------------------------------------------------------ |
| 1차 타깃                | 만 19~34세, 사회초년생·프리랜서, 월소득 200~350만 원               |
| 2차 타깃                | 1인 가구, 이직·휴직으로 소득이 바뀐 사람                           |
| 핵심 질문               | "나는 지금 뭘 받을 수 있고, 뭘 먼저 해야 손해를 안 보나?"          |
| 현재 대안               | 복지로에서 조건 입력 후 목록 받기, 커뮤니티 글 검색, 129 상담      |
| 부족한 것               | 목록은 받지만 **겹쳤을 때 무엇이 깨지는지** 아무도 알려주지 않는다 |
| 지불 의사가 생기는 순간 | 내가 놓친 돈이 구체적 금액으로 보일 때. 그리고 이미 손해를 본 뒤   |

## 3. 30초 경험 (Aha moment)

1. 호스트 앱 프로필로 나이·거주지·소득구간이 이미 채워져 있다. 사용자는 2~3개만 확인한다.
2. 30초 안에 카드 세 장이 나온다.
   - **받을 수 있는 돈**: 지금 신청 가능한 항목과 예상 금액 범위
   - **받으면 끊기는 것**: 지금 받고 있는 혜택 중 중단되는 항목
   - **순서를 바꾸면**: 지금 A를 신청하는 대신 C를 먼저 하면 남는 차액
3. 카드를 누르면 근거 조항과 기준일이 펼쳐진다. "2026-09-01 시행, 주택도시기금 운용 및 관리 규정 제O조".
4. 마지막 화면은 체크리스트다. 오늘 할 일 1개, 이번 달 안에 할 일 2개.

## 4. 제품 원칙

1. **단정하지 않는다.** "받을 수 있습니다"가 아니라 "요건 6개 중 5개 충족, 1개 확인 필요"로 말한다.
2. **근거 없는 관계는 만들지 않는다.** 모든 배타·충돌 엣지에 조항과 시행일을 붙인다. 근거를 못 찾으면 엣지를 넣지 않는다.
3. **금액은 범위로 보여준다.** 가구원 수·재산·임대료에 따라 달라지는 값을 점 하나로 찍지 않는다.
4. **오탐이 미탐보다 비싸다.** 후보를 넓게 뿌리지 않는다. 확신 등급이 낮은 항목은 "확인 필요"로 분리한다.
5. **온톨로지 용어를 노출하지 않는다.** 사용자는 혜택, 조건, 충돌, 순서만 본다.
6. **개인 데이터는 사용자 tenant에 가두고 삭제를 보장한다.** 소득·재산·보험 가입내역은 민감정보로 취급한다.

## 5. 추론 설계

### 5.1 세 단계를 분리한다

```text
[프로필] ──▶ 1. 자격 판정 ──▶ 후보 혜택 집합
                                   │
                                   ▼
                         2. 충돌 감지 (그래프)
                            - exclusive : 동시 수급 불가
                            - displaces : A 수급 시 B 중단 (방향 + 재신청 제한)
                            - income_offset : A가 B의 소득으로 산입
                            - requires : A 신청이 B의 전제
                                   │
                                   ▼
                         3. 조합 최적화
                            목적: Σ 기대 수령액 − Σ 상실액 − 신청 비용
                            제약: 배타, 선후, 신청 기간
```

### 5.2 대표적인 충돌 유형

| 유형      | 예시 (검증 필요)                                               | 추론 hop |
| --------- | -------------------------------------------------------------- | -------- |
| 직접 배타 | 청년월세지원 ↔ 청년 주거급여 분리지급                          | 1        |
| 소득 산입 | 지원금 수령 → 소득으로 잡힘 → 다른 급여의 소득 기준 초과       | 3        |
| 자격 연쇄 | 소득 발생 → 건강보험 피부양자 자격 상실 → 월 보험료 발생       | 3~4      |
| 선후 관계 | B 신청 전에 A를 받아야 B 요건이 성립                           | 1        |
| 실적 배분 | 카드 A와 B에 같은 지출을 나눠 쓰면 두 카드 모두 실적 구간 미달 | 2        |
| 중복 보장 | 실손 2건 가입 시 실제 부담액을 비례 보상, 보험료는 두 번 냄    | 2        |

세 번째 줄이 이 제품의 간판입니다. 지원금 20만 원을 받아 소득이 잡히고, 그 때문에 월 보험료가 새로 붙으면 실제 이득은 마이너스가 됩니다. 사람이 직접 계산하기 어렵고, 한 번 겪으면 되돌리기 어렵습니다.

### 5.3 불확실성을 값으로 다룬다

조건마다 근거 등급을 매기고, 등급이 리포트까지 전달되게 합니다.

| 등급 | 근거                     | 리포트 처리                              |
| ---- | ------------------------ | ---------------------------------------- |
| A    | 법령 조문                | 그대로 판정에 사용                       |
| B    | 부처 고시·공고·공식 안내 | 판정에 사용, 기준일 표시                 |
| C    | 지자체 조례, 상담 사례   | "확인 필요"로만 노출, 금액 합산에서 제외 |

자격 판정의 신뢰도는 조건 신뢰도의 최솟값으로 전파합니다. 하나라도 C면 그 혜택은 확정 후보가 아니라 확인 후보입니다.

### 5.4 최적화는 어렵지 않다

혜택 25개, 충돌 8쌍이면 충돌 그래프의 연결 요소가 작게 쪼개집니다. 요소별 완전탐색으로 충분하고, 규모가 커지면 ILP로 바꿉니다. 여기서 LLM을 쓰면 재현성이 깨지므로 쓰지 않습니다. LLM은 약관 텍스트에서 조건을 뽑고, 결과를 문장으로 바꾸는 데만 씁니다.

## 6. 온톨로지 스케치

```text
(:Benefit {iri, name_ko, agency, category, application_window, as_of})
  -[:REQUIRES {group, optional}]->(:Condition)
  -[:USES_HOUSEHOLD]->(:HouseholdDefinition)
  -[:EXCLUDES {type, basis, effective_from}]->(:Benefit)
  -[:DISPLACES {cooldown_days, basis}]->(:Benefit)
  -[:COUNTS_AS_INCOME {ratio, basis}]->(:IncomeRule)
  -[:VALUE_FROM]->(:ValueFunction)

(:Condition {iri, field, operator, threshold, unit, legal_basis})
  -[:ON_FIELD]->(:ProfileField)
  -[:CITED_BY]->(:Clause)

(:HouseholdDefinition {iri, includes_parents, includes_children, note})
(:IncomeRule {iri, inclusion, conversion_rate, basis})
(:ValueFunction {iri, kind, formula, cap, period})
(:Clause {iri, source, article, text, effective_from, effective_to, url})
(:ProfileField {iri, name_ko, type, sensitivity})
```

설계에서 지켜야 할 것 세 가지.

1. **배타는 대칭이 아니다.** `EXCLUDES`는 양쪽에 걸지만 `DISPLACES`는 방향과 시간(중단 시점, 재신청 제한)이 붙습니다. 대칭으로 모델링하면 "B를 받으면 A도 못 받는다"는 틀린 답이 나옵니다.
2. **가구 정의를 조건에서 분리한다.** 같은 사람이 제도마다 다른 가구로 계산됩니다. 부양의무자 포함 여부가 제도별로 다르기 때문에, 사용자 속성에 가구원 수를 하나만 저장하면 반드시 틀립니다.
3. **모든 엣지에 `Clause`와 `as_of`를 건다.** 이게 "근거 조항 명시" 요구사항을 데이터 구조로 강제하는 방법입니다. 근거가 없는 엣지는 적재 단계에서 거부합니다.

### 지금 하지 않는 것

- 보험 영역 (보험업법상 비교·추천은 중개 등록 이슈가 있어 v2로 미룸)
- 자동 신청 대행, 서류 자동 작성
- MyData 연동 (허가·제휴 없이는 불가)
- 전국 지자체 확장 (수도권 3개 시·도만)
- LLM이 조건을 직접 판정하는 구조
- "받을 수 있는 돈 총액" 같은 단일 숫자 마케팅

## 9. 화면 구성

```text
[진입]  "놓치고 있는 돈이 있는지 30초만 확인해 볼까요?"
   │
[확인]  나이 · 거주지 · 소득구간 · 현재 받는 혜택 (3문항, 나머지는 prefill)
   │
[리포트]
   ├─ 지금 받을 수 있는 돈        3건 · 예상 32~48만 원
   ├─ 받으면 끊기는 것           1건 · 주의
   ├─ 순서를 바꾸면              +15만 원 (C 먼저 → A 나중)
   └─ 근거                    조항 · 시행일 · 확인 필요 표시
   │
[체크리스트]  오늘 1개, 이번 달 2개
   │
[공유 카드]   금액은 숨기고 "3건 발견" 형태로 익명화
```

미니앱이므로 설치·가입·결제 화면을 만들지 않습니다. 호스트 세션을 그대로 쓰고, 리포트는 호스트 알림으로 리마인드합니다. 리마인드가 이 제품의 재방문을 만듭니다. 신청 기간이 있는 혜택은 기간이 다가올 때 다시 불러야 합니다.

## 10. 아키텍처 연결

```text
Host App (미니앱 WebView / 네이티브 임베드)
      │  profile (이미 존재) + 확인 3문항
      ▼
FastAPI /benefit API
      │
      ├─ 룰 엔진 (Python, 수치·가구 판정)
      ├─ GraphDB (혜택·조건·충돌·조항 원장, 버전 고정)
      └─ Planner (충돌 요소별 완전탐색)
      │
      ▼
Neo4j 투영 ── 충돌 경로 시각화, 유사 사용자 비교
      │
      └── citation · clause · as_of · confidence
```

- 새 도메인 모듈은 `src/app/benefit/`에 둡니다. `src/app/card/`와 같은 패턴입니다.
- MCP 도구는 `benefit.eligibility`, `benefit.conflicts`, `benefit.plan`, `benefit.clause` 네 개로 제한합니다.
- 온톨로지는 후보 검색과 충돌 증명에 쓰고, 수치 판정은 코드로 둡니다. OWL 2 RL은 수치 비교와 예외 처리에 약합니다.
- 리포트는 생성 시점의 온톨로지 버전과 조항 스냅샷을 함께 저장합니다. 법령이 바뀌어도 "그때 왜 그렇게 말했는지" 재현할 수 있어야 합니다.
- 1차 구현은 전체 파이프라인이 아니라 "혜택 25개 + 리포트 1종"의 얇은 수직 슬라이스로 시작합니다.

## 11. 수익 모델과 이해상충

| 플랜 | 가격       | 내용                                         |
| ---- | ---------- | -------------------------------------------- |
| 무료 | 0원        | 후보 3건, 충돌 1건, 공유 카드                |
| 심층 | 9,900원    | 전체 후보, 순서 최적화, 근거 조항, 알림      |
| 구독 | 월 4,900원 | 조건 변경 감지, 신청 기간 알림, 새 혜택 알림 |
| B2B  | 별도       | 카드사·보험사 제휴, 지자체 복지 안내         |

제휴가 붙는 순간 "유리한 조합"과 "우리가 받는 수수료"가 충돌합니다. 추천 정렬에 제휴 여부를 쓰지 않는다는 규칙을 먼저 정하고, 리포트에 제휴 표시를 노출해야 합니다. 이걸 어기면 제품의 유일한 차별점이 사라집니다.

MVP에서는 결제를 붙이지 않고 "심층 리포트 신청"으로 지불 의향만 측정합니다.

## 12. 리스크와 완화

| 리스크                     | 완화                                                                    |

## 16. 결정 기록: 카드 실적 배분을 v0로 (2026-10-30)

지원금 대신 카드 실적 배분부터 만듭니다. 리스크가 낮고 6주 안에 끝까지 돌려 볼 수 있는 쪽이기 때문입니다.

| 기준      | 카드 실적 배분                 | 지원금                             |
| --------- | ------------------------------ | ---------------------------------- |
| 데이터    | 호스트 앱 거래내역 (입력 없음) | 소득·재산·가구원 수 입력 필요      |
| 로직      | 상품설명서 한 장, 숫자와 구간  | 법령·고시·조례·가구 정의·재산 환산 |
| 정답      | 결정적, 하나                   | 해석 분기, 오탐 가능               |
| 검증      | 다음 달 명세서                 | 신청 후 수주~수개월                |
| 실패 비용 | 다음 달에 재시도               | 환수·이자·부정수급 기록            |
| 유지비    | 카드 5~10개                    | 혜택 25개 + 지자체 수천 개         |

핵심 차이는 **정답이 하나인가**입니다. 거래내역과 약관만 있으면 계산이 결정적이라 오탐이 구조적으로 줄어듭니다. 지원금은 "이 소득이 산입되는가"부터 해석이 갈리고, 그 해석이 틀리면 사용자가 환수당합니다.

### v0 범위 (지원금 MVP를 대체)

| 영역     | 내용                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 입력     | 호스트 거래내역 + 보유 카드 2~5장 선택                                       |
| 온톨로지 | 카드 10개, 혜택 규칙 40개, 업종 20개, 실적 제외 규칙                         |
| 계산     | 카드별 현재 실적 → 다음 구간까지 남은 금액 → 구간 혜택 → 필요 추가 지출 비교 |
| 출력     | 이번 달 배분안 1장: "여기서 이 카드", "이 카드는 그만", "채우지 마세요"      |
| 알림     | 실적 마감 D-7, 구간 미달 경고                                                |
| 검증     | 다음 달 명세서 대조, 예측 오차 기록                                          |

### 지금 하지 않는 것 (v0)

- 카드 발급 추천, 신규 카드 비교 (여신금융 대리점 등록 이슈)
- 지원금, 보험 (v1 이후)
- 거래 취소·환불 반영 실시간 처리 (일 배치로 충분)
- 사용자가 이미 긁은 거래의 재배치 제안 (옮길 수 없는 지출은 제안하지 않음)

### 전제 조건

호스트 앱이 카드 사용내역을 갖고 있어야 합니다. 없으면 거래내역 입력을 받아야 하고, 그 시점에 지원금 대비 난이도 우위가 사라집니다. 이 전제가 깨지면 결정을 다시 봅니다.

### 남는 약점

임팩트가 작아 공유와 지불 의향이 낮습니다. 수익화도 제휴 없이는 어렵습니다. v0의 목적은 수익이 아니라 **계산 정확도와 재방문율을 확인하는 것**입니다. 이 두 숫자가 나오면 지원금으로 넓힙니다.

## 17. 전제 변경: 거래내역 없음 (2026-10-30)

16절의 전제가 깨졌습니다. 호스트 앱에 카드 사용내역이 없습니다. 결정을 다시 계산합니다.

### 무엇이 달라지고 무엇이 남는가

| 항목             | 거래내역 있을 때 | 없을 때                 |
| ---------------- | ---------------- | ----------------------- |
| 데이터 우위      | 입력 0개         | 입력 4개 (수동)         |
| 해석 리스크 없음 | 유지             | 유지                    |
| 결과 검증 가능   | 유지             | 유지                    |
| 규제 접점 낮음   | 유지             | 유지                    |
| 자동 집계·알림   | 가능             | 불가, 리마인드만        |
| 리텐션           | 자연 발생        | **미검증, 최대 리스크** |

카드가 쉬운 이유는 데이터가 아니라 **해석할 것이 없다**는 점이었습니다. 지원금의 위험은 "이 소득이 산입되는가"를 틀려 사용자가 환수당하는 것이고, 이건 거래내역이 있어도 사라지지 않습니다. 카드는 입력이 번거로워질 뿐 틀릴 여지가 없습니다. 리스크 기준으로는 카드가 계속 우위입니다.

### 바뀐 형태: 월 1회 계산기

| 입력 | 카드 선택, 카드별 이번 달 사용액, 남은 예상 지출, (선택) 큰 지출 예정                |
| ---- | ------------------------------------------------------------------------------------ |
| 출력 | "N원 더 채우면 M원 이득" / "채우지 마세요" / "이 카드는 한도 소진, 남은 지출은 저쪽" |
| 주기 | 월 1회. 실적 마감 D-7 리마인드                                                       |
| 계산 | 결정적. 거래 취소·제외 항목은 사용자가 입력한 값 기준으로만 다룸                     |

### 계획 변경: 빌드 2주 + 관찰 4주

만드는 비용이 낮아졌으므로 리텐션을 먼저 확인합니다. 다만 재입력률은 한 달을 기다려야 나오므로 판정은 6주째입니다. 상세 명세는 `docs/CARD_ALLOCATION_V0.md`로 분리했습니다.

| 기간  | 결과물                                     |
| ----- | ------------------------------------------ |
| 1주   | 카드 10개 약관 정리, 계산 규칙, 계산기 API |
| 2주   | 화면 1장, 배포 (월 20일 이전)              |
| 3~5주 | 사용자 50명, 결과 노출, 명세서 대조        |
| 6주   | 재입력률 판정, 유지 또는 지원금 전환       |

| 프로브 지표               | 기준                                 |
| ------------------------- | ------------------------------------ |
| 입력 완료율               | 80% 이상                             |
| 다음 달 재입력률          | 30% 이상                             |
| 예측 오차                 | 1% 미만 (명세서 대조)                |
| "채우지 마세요" 노출 비율 | 20% 이상 (이 조언이 실제로 나오는지) |

재입력률이 30%를 밑으면 카드 계산기는 접습니다. 입력 부담이 같은데 임팩트가 큰 지원금으로 갑니다. 지원금은 1회성으로도 성립하고, 카드 계산기는 반복되지 않으면 가치가 0에 가깝습니다.

### 남은 확인 사항

호스트 앱이 가진 데이터가 가입정보 수준인지, 소득구간·거주지까지 있는지에 따라 지원금 쪽 입력 부담이 달라집니다. 프로브와 별개로 확인이 필요합니다.
