# pypo 전략: 하나의 엔진, 두 개의 채널

> 상태: v1 (2026-10-30). 제품·문서·로드맵이 이 문서와 어긋나면 이 문서를 먼저 고칩니다.

## 1. 한 문장

**pypo는 규칙과 관계를 근거와 함께 계산해 "결정"을 내주는 지식 엔진이다. B2C 앱은 이 엔진을 한 층씩 증명하는 시연장이고, B2B는 같은 엔진을 다른 조직에 파는 채널이다.**

## 2. 왜 B2B와 B2C를 같이 가는가

둘은 별개의 사업이 아니라 같은 엔진의 두 출구입니다.

|                    | B2C                                          | B2B                                                 |
| ------------------ | -------------------------------------------- | --------------------------------------------------- |
| 역할               | 수요 증명, 지식 큐레이션, 데모               | 수익, 규모                                          |
| 파는 것            | 결정 하나 ("이 카드는 채우지 마세요")        | 엔진과 도메인 지식 (API, MCP 도구, 온톨로지 템플릿) |
| 엔진에 돌려주는 것 | 검증된 도메인 데이터, 오탐 사례, 실사용 지표 | 새 도메인, 대규모 적재 요구, 멀티테넌시 요구        |
| 대표 고객 가설     | 사회초년생, 카드 2~5장 보유자                | 카드사·핀테크(혜택 엔진), 복지 상담 기관(충돌 감지) |

선순환은 이렇습니다. B2C에서 손으로 다듬은 온톨로지(카드 약관, 혜택 충돌)가 그대로 B2B 템플릿이 됩니다. B2B 고객은 "실제 사용자가 쓰는 엔진"이라는 증거를 B2C에서 봅니다.

지켜야 할 경계도 있습니다.

- **B2C 개인 데이터는 B2B로 넘기지 않습니다.** 공유하는 것은 엔진과 공공 지식(약관, 법령)뿐입니다.
- **B2B 제휴가 B2C 추천 순서를 바꾸지 않습니다.** 제휴 여부는 정렬에 쓰지 않고, 제휴가 있으면 화면에 표시합니다. 이 원칙이 깨지면 B2C의 신뢰도와 B2B 데모 가치가 함께 사라집니다.

## 3. 계단: 단계마다 엔진의 층을 하나씩 더 쓴다

| 단계  | 제품                          | 새로 증명하는 엔진 층                               | 넘어가는 조건                                                             | 실패하면                                           |
| ----- | ----------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| **1** | 카드 실적 배분 계산기         | 규칙 엔진, 조항·기준일 근거, 버전이 있는 데이터     | 입력 완료율 80% 이상, 다음 달 재입력률 30% 이상, 명세서 대조 오차 1% 미만 | 카드 계산기를 접고 2단계(지원금)로 바로 이동       |
| **2** | 카드 + 지원금 충돌 지도       | 온톨로지(충돌 관계), SHACL 검증, 그래프 경로로 설명 | 오탐 신고율 2% 미만, 리포트 도달률 55% 이상                               | 오탐 신고율 5% 초과면 중단, 세그먼트를 좁혀 재시도 |
| **3** | "이거 받으면 뭐가 끊겨?" 질의 | 에이전트, MCP 도구(`benefit.*`), 근거가 붙은 답변   | 골든 질문셋 groundedness 목표 달성 (목표치는 2단계 종료 시 확정)          | 질의를 정해진 리포트로 되돌림                      |
| **4** | B2B 파일럿                    | 멀티테넌시, 온톨로지 템플릿, 외부 MCP 클라이언트    | 유료 파일럿 1곳                                                           | 고객 가설 재검토                                   |

이 순서는 `docs/B2C_BENEFIT_GRAPH.md`의 판단을 따릅니다. 그래프가 제값을 하는 곳은 충돌 감지이고, 금액 계산은 코드로 둡니다. 그래서 1단계 카드 계산기에 온톨로지가 없는 것은 빠뜨린 게 아니라 순서입니다.

## 4. 플랫폼 로드맵과의 연결

README 로드맵은 엔진 쪽 순서입니다. 엔진 작업은 **다음 계단이 필요로 할 때만** 당겨옵니다. 계단보다 먼저 만들지 않습니다.

| README 로드맵 단계                 | 필요해지는 계단        |
| ---------------------------------- | ---------------------- |
| 0. Foundation                      | 1단계 (완료 수준)      |
| 1. Ontology core                   | 2단계                  |
| 3. Hybrid retrieval 중 Neo4j 투영  | 2단계 (충돌 경로 설명) |
| 2. Agent loop                      | 3단계                  |
| 3. Hybrid retrieval 나머지         | 3단계                  |
| 4. Ingestion at scale, 5. Platform | 4단계                  |
| 6. Ecosystem                       | 4단계 이후             |

1단계 진행 중에 할 수 있는 엔진 작업은 하나뿐입니다. **카드 카탈로그의 데이터 구조를 2단계 온톨로지로 옮길 수 있게 맞춰 두는 것**입니다. 모든 구간에 조항(`clause`)과 기준일(`as_of`)을 붙이는 규칙은 이미 지키고 있습니다. JSON을 RDF로 옮기는 작업 자체는 2단계에서 합니다.

## 5. 지금 하지 않는 것

- **직무 생존 지도.** 2026-10-30에 폐기했습니다. 혼자 개발하면서 B2C를 두 개 동시에 검증할 수 없고, 혜택 도메인이 계산 정확도를 검증하기 더 쉽습니다.
- **카드 단건 결제 추천을 주력으로 내세우는 것.** 뱅크샐러드·카드고릴라가 이미 하는 영역입니다. 배분 결과를 보조하는 기능(P1)으로만 둡니다.
- 3단계 전에 범용 에이전트·채팅 기능을 만드는 것.
- 4단계 전에 멀티테넌시를 고도화하는 것. 데이터 모델에 tenant를 넣는 것까지만 합니다(README 설계 원칙 8).
