# AI 직원 pypo: 계획을 받아 매일 PR을 올리는 동료

> 상태: 설계 v0 (2026-10-30). 구현 전입니다.
> 이름: **pypo**. 플랫폼과 같은 이름을 쓰는 이 저장소의 얼굴입니다. 문서와 코드에서 플랫폼과 헷갈리지 않도록 모듈 이름은 `devbot`으로 둡니다 (`src/app/agents/devbot/`, 이 문서 `DEVBOT.md`).

## 1. 한 줄 정의

**내가 GitHub Issue로 계획을 쓰면, 매일 1~2개를 골라 구현하고 PR을 올리고, 리뷰를 받으면 고치고, 배운 것을 기억하는 AI 동료.**

- 매일 PR을 뽑아내는 스크립트가 아니라 **정체성과 기억을 가지고 일하면서 성장하는 동료**를 목표로 합니다.
- 처음에는 성능이 약해도 됩니다. 대신 **AI API 비용은 0원**으로 시작합니다.
- 이 직원은 pypo 플랫폼의 첫 번째로 실제 동작하는 에이전트이고, 코드 작성까지 직접 합니다.

## 2. 출발점

[kagura-chen](https://github.com/kagura-chen)에서 **"AI가 사람 곁에서 일하면서 스스로 성장한다"**는 생각을 얻었습니다. 가져온 것은 이 생각 하나이고, 구조와 도구는 pypo의 원칙과 이 저장소의 사정에 맞춰 따로 정합니다.

pypo 쪽 판단 기준은 다음과 같습니다.

- **코드 작성까지 직접 합니다.** 계획, 구현, 회고가 모두 pypo 플랫폼 위의 LangGraph 그래프입니다. 그래야 12절의 진화가 코드 작성 능력 자체에 닿습니다. 바꿀 수 있는 것은 모델뿐입니다 (6절).
- **LLM은 필요한 곳에만 씁니다.** 고르기, 검증, PR 생성은 일반 코드가 처리합니다. `B2C_BENEFIT_GRAPH.md`에서 정한 원칙과 같습니다.
- **이 저장소 하나에서만 일합니다.** 외부 기여, 별도 계정은 없습니다.
- **기억은 pypo 온톨로지로 이어집니다** (8절). 플랫폼의 "지식 자산화"를 자기 자신에게 먼저 적용합니다.

## 3. 구조

```text
GitHub Actions 정기 실행 (또는 로컬 Mac, 6절)
 ├─ day loop (매일 06:00 KST)
 │    후속 처리 → 작업 고르기 → 구현 → 검증 → PR 생성 → 회고
 └─ follow-up loop (2~3시간마다)
      리뷰 코멘트 반영, CI 실패 수정 (새 작업은 하지 않음)

pypo (모두 pypo 플랫폼 위에서 직접 만듦)
 ├─ 작업 흐름   상태 머신과 관문 (4절)
 ├─ 코드 작성   LangGraph 노드. 입력은 코드가 고른 파일 내용, 출력은 찾아 바꾸기(SEARCH/REPLACE) 또는 덧붙일 코드 블록 (4절 3~4단계)
 ├─ 정체성      페르소나 파일, 커밋 작성자 pypo-agent, pypo 라벨 (9절)
 ├─ 기억        agent/memory/*.md → 나중에 pypo 온톨로지로 (8절)
 ├─ 진화        스킬 문서, 재실행 평가, 자기 개선 제안 (12절)
 └─ 기록        일일 요약, 머지율, PR당 비용 (10절)

모델 (설정으로 교체)
 └─ DEVBOT_MODEL = "provider:model" (6절)
```

코드 위치: `src/app/agents/devbot/`. 실행: `uv run python -m src.app.agents.devbot day|followup [--dry-run] [--issue N]`.

범용 Agent DB 모델이나 workflow DSL에는 아직 맞추지 않습니다. 독립된 그래프로 먼저 만들고, 3단계(STRATEGY.md)에서 일반화합니다.

## 4. 작업 흐름 (day loop)

LLM은 표시된 두 단계에서만 씁니다. 나머지는 일반 코드가 결정적으로 처리합니다.

| 단계           | 주체       | 하는 일                                                                                     | 다음 단계로 가는 조건 (관문)                                                                                                                                |
| -------------- | ---------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 후속 처리   | 코드 + LLM | follow-up loop를 먼저 한 번 실행                                                            | 항상 진행                                                                                                                                                   |
| 2. 작업 고르기 | 코드       | `bot-ready` 이슈 중 가장 오래된 것                                                          | 리뷰 대기 봇 PR이 3개 미만이고, 이슈가 템플릿 필수 항목을 모두 채움                                                                                         |
| 3. 구현        | **LLM**    | 찾아 바꾸기(SEARCH/REPLACE) 블록, 또는 덧붙일 코드 블록 생성                                | 형식이 맞고, SEARCH가 한 곳과 정확히 일치하고, 금지 경로와 기존 테스트를 건드리지 않음. 범위를 벗어나야 하면 짧은 질문을 남기고 `bot-question` 라벨 후 종료 |
| 4. 검증        | 코드       | ruff가 안전하게 고칠 수 있는 것은 먼저 고침. ruff, pytest, 웹을 건드렸으면 `pnpm typecheck` | 모두 통과하고 이슈가 이름으로 요구한 테스트가 모두 있음. 실패하면 에러 출력을 붙여 3으로, 최대 3회                                                          |
| 5. PR 생성     | 코드       | 브랜치 `pypo/<이슈번호>-<slug>`, 커밋, 푸시, PR (`Closes #N`, `pypo` 라벨), CI 수동 실행    | 변경이 400줄 이하                                                                                                                                           |
| 6. 회고        | **LLM**    | 이번 작업에서 배운 점을 기억에 기록                                                         | 항상 진행                                                                                                                                                   |

끝내 실패하면 PR을 만들지 않고, 이슈에 마지막 에러와 시도 내역을 남긴 뒤 `bot-failed` 라벨을 붙입니다.

**follow-up loop:** 열린 봇 PR마다 다음을 처리합니다.

1. 새 리뷰 코멘트가 있으면 4~6단계를 다시 돌려 같은 브랜치에 커밋을 추가합니다.
2. CI가 실패했으면 에러 출력을 붙여 4~6단계를 다시 돕니다.
3. 머지되거나 닫힌 PR은 7단계(회고)로 보냅니다.

## 5. 이슈 계약

성능이 약한 모델은 저장소를 스스로 둘러보며 판단하지 못합니다. 그래서 **판단은 이슈가 하고, 모델은 좁은 범위의 코드 작성만** 합니다. 결과물 품질은 이슈 품질이 정합니다.

이슈 템플릿 (`.github/ISSUE_TEMPLATE/bot-task.yml`) 필수 항목:

| 항목                | 예시                                                          |
| ------------------- | ------------------------------------------------------------- |
| 목표 (한 문장)      | `plan_allocation`이 실적 미입력 카드를 거절한다               |
| 수정할 파일 (1~3개) | `src/app/card/calculator.py`, `tests/test_card_calculator.py` |
| 완료 기준           | 실적이 빠진 카드를 넘기면 `ValueError`, 메시지에 카드 ID 포함 |
| 통과해야 할 테스트  | `test_missing_spend_is_rejected_not_treated_as_zero`          |
| 하지 않을 것        | API 응답 형식은 바꾸지 않는다                                 |

필수 항목이 비어 있으면 봇은 그 이슈를 고르지 않습니다. 테스트 이름이 없으면 검증이 ruff·pytest뿐이라 아무것도 안 한 답도 통과하므로, 테스트도 필수입니다(#3). 리팩터링처럼 테스트를 고치지 않는 이슈는 사람이 실패하는 테스트를 먼저 넣어 둡니다.

**라벨**

| 라벨           | 의미                                                   |
| -------------- | ------------------------------------------------------ |
| `bot-ready`    | 봇이 가져가도 되는 작업                                |
| `bot-question` | 봇이 질문을 남김. 답한 뒤 라벨을 지우면 다시 후보가 됨 |
| `bot-failed`   | 3회 시도 후 실패. 이슈를 쪼개거나 직접 처리            |

## 6. 모델: AI API 비용 0원

`DEVBOT_MODEL`에 `"provider:model"` 형식으로 지정합니다(`settings.search_model`과 같은 방식). 코드를 바꾸지 않고 아래 세 가지를 오갈 수 있습니다.

| 방법                                  | 비용                               | 특징                                                                      | 한계                                                                         |
| ------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **A. 로컬 Mac + Ollama**              | 0원                                | M2 16GB에서 7~8B 코딩 모델이 초당 20~30토큰                               | 실행 시각에 Mac이 켜져 있어야 함                                             |
| **B. GitHub Models (Actions 안에서)** | 0원 (무료 할당량)                  | API 키 없이 Actions 토큰(`models: read`)으로 호출, 모델 성능은 A보다 좋음 | 요청당 입력 길이와 하루 호출 수 제한이 빡빡함. 시작 전에 현재 한도 확인 필요 |
| **C. Actions 기본 서버에서 Ollama**   | 0원 (공개 저장소는 Actions 무제한) | 외부 의존 없음                                                            | GPU 없이 CPU로만 돌아 느림. 모델은 캐시로 보관                               |

**운영 방침:** 개발과 테스트는 A로 빠르게 반복합니다. 무인 운영은 B로 시작하고, 한도가 부족하면 C로 바꿉니다.

**비용 상한:** 실행 한 번에 LLM 호출 20회까지만 씁니다. 0원이라도 무료 할당량을 지키고 무한 루프를 막기 위해서입니다.

**성능이 약한 모델을 전제로 한 설계**

- 모델에게 주는 정보는 코드가 고릅니다. 이슈에 지정된 파일과 `AGENTS.md`만 넣고, 모델이 직접 파일을 찾아다니게 하지 않습니다.
- 출력 형식을 고정합니다. 바꿀 부분만 찾아 바꾸기(SEARCH/REPLACE) 블록으로 받고, 형식이 틀리거나 SEARCH가 원본과 맞지 않으면 버리고 다시 요청합니다. 사전 확인(2026-10-30)에서 파일 전체를 다시 쓰게 하자 7B 모델이 기존 테스트 7개를 빠뜨렸기 때문입니다. 출력이 짧아져 속도도 빨라집니다.
- 별도의 계획 단계는 두지 않습니다. M1에서 계획 단계를 넣었더니 7B 모델이 165초를 쓰고도 계획 대신 이슈를 되풀이하는 질문을 냈습니다. 이슈 자체가 계획 역할을 합니다.
- 모델에는 수정할 파일 전체와, 참고 모듈 중 이슈에 이름이 나온 정의만 발췌해 줍니다. 입력이 짧을수록 7B 모델이 빠르고 정확합니다.
- 덧붙이기만 하는 작업은 SEARCH/REPLACE 없이 코드 블록만 받아도 됩니다. 새 코드 맨 위의 import는 파일의 import 영역으로 옮기고, 쓰지 않는 import 같은 기계적 오류는 ruff가 고칩니다. 같은 입력이면 모델은 같은 실수를 반복하기 때문입니다.
- 기존 테스트 함수가 사라지면 거부합니다. 테스트를 지워도 pytest는 실패하지 않기 때문입니다.
- 성공 판정은 테스트가 합니다. 모델의 자기 평가는 쓰지 않습니다.

**알고 시작할 한계:** 처음에 할 수 있는 일은 "하루 기능 1~2개"가 아니라 **"하루에 아주 작은 작업 1~2개"**입니다. 예를 들어 함수 하나에 테스트 추가, 검증 규칙 하나, 화면 문구 수정 정도입니다. 더 강한 모델로 바꾸면 이슈 범위만 넓히면 됩니다.

## 7. 안전장치

모두 **프롬프트가 아니라 코드로** 강제합니다.

| 장치             | 내용                                                                                                                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 수정 금지 경로   | `migrations/`, `.github/`, `.env*`, `uv.lock`, `pnpm-lock.yaml`, `agent/persona.md`, 안전장치 코드(`src/app/agents/devbot/guards.py`), 평가 코드와 문제 세트(`agent/evals/`). 파일 쓰기 도구가 거부함 |
| 허용 경로        | 이슈에 지정된 파일과, 이름이 `tests/test_*.py`인 새 파일만                                                                                                                                            |
| 실행 가능한 명령 | 허용 목록만 (`uv run pytest`, `uv run ruff check`, `pnpm typecheck`)                                                                                                                                  |
| 검증 샌드박스    | ruff·pytest는 Docker 컨테이너에서 실행. 네트워크 없음, worktree만 마운트, 의존성은 `uv.lock`으로 미리 만든 이미지. Docker가 없으면 실행하지 않음                                                      |
| 브랜치           | `pypo/*`에만 푸시. main 직접 푸시 불가 (브랜치 보호 규칙으로도 막음)                                                                                                                                  |
| 변경 규모        | 변경 400줄 초과 시 PR을 만들지 않음                                                                                                                                                                   |
| 리뷰 대기 상한   | 리뷰 대기 봇 PR 3개 이상이면 새 작업을 시작하지 않음                                                                                                                                                  |
| 호출 상한        | 실행 한 번에 LLM 호출 20회                                                                                                                                                                            |

리뷰와 머지는 항상 사람이 합니다.

## 8. 기억

README의 "지식 자산화: 대화 로그가 아니라 버전 관리되는 온톨로지로 지식이 축적된다"를 pypo 자신에게 적용합니다. 실행할 때마다 찾아서 조립하기보다, 작업할 때마다 배운 것을 정리해 쌓아 둡니다.

**v1: 저장소 안의 마크다운**

```text
agent/
├── persona.md          # 정체성, 말투, 일하는 원칙 (사람만 수정)
└── memory/
    ├── conventions.md  # 이 저장소의 규칙 (리뷰에서 지적받은 것 포함)
    ├── mistakes.md     # 실패와 원인, 다음에 피하는 방법
    └── log/            # 작업별 회고 (YYYY-MM-DD-#N.md). 지표를 잴 때(M5) 추가
```

- **쓰기:** 7단계(회고)에서 씁니다. 기억 변경은 해당 PR에 함께 들어가므로, 사람이 리뷰를 통해 기억도 검수합니다.
- **읽기:** 3단계(구현)에서 `conventions.md`와 `mistakes.md`를 모델 입력에 넣습니다. 입력 길이를 지키기 위해 각 파일은 50줄 이하로 유지하고, 넘치면 회고 단계에서 요약합니다.
- **기록할 때:** 배운 것이 있을 때만 씁니다. 실패했다가 통과한 작업(그 실패와 해결)과 리뷰 지적(M3 이후)입니다. 첫 시도에 통과한 작업은 `log/`에만 남깁니다.
- **모델이 쓰는 것:** 파일 전체가 아니라 `[발생 상황] → [원인] → [해결]` 한 항목입니다. 덧붙이기, 중복 확인, 50줄 상한은 코드가 맡습니다. 작은 모델에게 병합을 시키면 기존 내용을 덮어씁니다. 입력에는 에러 로그 원문 대신 마지막 실패 요약과 통과한 수정만 넣습니다.
- **쓰지 않는 것:** 구조 결정(ADR)은 사람이 정합니다. pypo는 질문(`bot-question`)으로 남깁니다.
- **GitHub Wiki에 직접 푸시하지 않습니다.** 리뷰 없이 기억이 프롬프트로 들어가고, `pypo/*` 브랜치 규칙을 우회하며, Actions 기본 토큰으로는 위키에 쓸 수 없습니다. 위키 화면이 필요해지면 `agent/memory/`를 위키로 복사하는 Action만 붙입니다.
- **효과 확인:** 기억을 넣었을 때 통과율이 오르는지 재실행 평가(12절, M6)로 봅니다.

**v2: pypo 온톨로지로 이전.** STRATEGY 2단계에서 온톨로지 계층이 생기면 옮깁니다. 이렇게 되면 pypo는 "자기 기억이 자기 플랫폼의 온톨로지에 쌓이는 첫 번째 에이전트"가 되고, B2B 데모로도 쓸 수 있습니다.

## 9. 정체성

**별도 GitHub 계정은 만들지 않습니다.** pypo는 이 저장소 안에서만 사는 에이전트이고, 정체성도 저장소 안에 둡니다.

- **페르소나 파일:** `agent/persona.md`에 이름(pypo), 말투, 일하는 원칙을 적습니다. PR 본문과 이슈 코멘트를 이 말투로 쓰고, 끝에 `— pypo` 서명을 붙입니다. 사람만 수정합니다.
- **커밋 작성자:** `pypo-agent <pypo-agent@noreply.localhost>`. 어떤 GitHub 계정과도 연결되지 않는 주소라, 나중에 누가 같은 이름의 계정을 만들어도 커밋이 그쪽에 붙지 않습니다.
- **구분 표시:** 브랜치 `pypo/*`, 라벨 `pypo`. 리뷰 대기 상한(7절)과 지표(10절)는 이 라벨로 셉니다.

**GitHub 권한은 실행 환경의 것을 씁니다.**

| 실행 환경      | 쓰는 권한                                                     | PR 작성자 표시        | CI                                                                                        |
| -------------- | ------------------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------- |
| 로컬 Mac       | 이미 로그인된 `gh` 계정                                       | 저장소 주인           | 그대로 돎                                                                                 |
| GitHub Actions | 기본 토큰 `GITHUB_TOKEN` (contents·pull-requests·issues 쓰기) | `github-actions[bot]` | 자동으로는 안 돎. PR 생성 직후 pypo가 `gh workflow run ci.yml --ref <브랜치>`로 직접 실행 |

Actions에서 쓰려면 사람이 두 가지를 해 둡니다. ci.yml에 `workflow_dispatch:` 트리거를 추가하고, 저장소 설정에서 "Allow GitHub Actions to create and approve pull requests"를 켭니다. 기본 토큰으로 일으킨 이벤트는 새 워크플로를 실행하지 않는데, `workflow_dispatch`만은 예외이기 때문입니다.

## 10. 기록과 지표

**일일 요약:** day loop가 끝나면 고정 이슈("pypo 일지")에 코멘트를 남깁니다. 내용은 오늘 한 일, 실패한 일, 남긴 질문, 사용한 호출 수입니다. 일지 이슈는 사람이 만들어 둡니다. 없으면 요약을 출력만 합니다.

**작업 기록:** `agent/memory/log/`의 각 회고에 이슈 번호, PR 번호, 시도 횟수, LLM 호출 수, 결과를 남깁니다.

| 지표                  | 의미                                                | 처음 목표 |
| --------------------- | --------------------------------------------------- | --------- |
| 수정 없이 머지된 비율 | 리뷰 코멘트 없이 머지된 봇 PR 비율                  | 30% 이상  |
| 최종 머지율           | 후속 처리를 포함해 결국 머지된 비율                 | 60% 이상  |
| 검증 통과율           | 고른 이슈 중 5단계를 통과한 비율                    | 50% 이상  |
| 같은 지적 반복        | `conventions.md`에 있는 내용으로 다시 지적받은 횟수 | 0         |
| PR당 리뷰 시간        | 사람이 쓴 시간 (직접 기록)                          | 10분 이하 |

## 11. 단계

| 단계   | 추가되는 것                                                          | 끝났다고 보는 기준                                                          |
| ------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **M0** | `AGENTS.md`, 이슈 템플릿, 라벨, `agent/persona.md`                   | 템플릿을 채운 `bot-ready` 이슈 3개                                          |
| **M1** | 로컬 미리 보기(`--dry-run`): 작업 흐름 2~4단계 + 코딩 루프, 모델은 A | 이슈 3개 중 2개가 검증 통과                                                 |
| **M2** | 실제 PR 생성 + 일일 요약                                             | 수정 없이 머지할 수 있는 PR 1개                                             |
| **M3** | follow-up loop: 리뷰 코멘트와 CI 실패 반영                           | 리뷰 지적을 반영한 PR 1개 머지                                              |
| **M4** | 기억: 회고 작성, 구현 입력에 기억 반영                               | 같은 지적을 두 번 받지 않음                                                 |
| **M5** | Actions 무인 운영, 모델 B 또는 C                                     | 일주일 운영, 10절 지표 측정                                                 |
| **M6** | 재실행 평가 + 스킬 문서 (12절 1단계)                                 | 문제 10개 이상 확보, 스킬 문서를 넣었을 때 통과율이 넣지 않았을 때보다 높음 |
| **M7** | 자기 개선 제안 (12절 2단계)                                          | 평가 점수를 올린 자기 개선 PR 1개 머지                                      |

M1 전에 15분짜리 사전 확인을 합니다. 7B급 코딩 모델을 Ollama로 받아, 5절 방식으로 실제 pypo의 작은 작업 하나를 시켜 봅니다. 테스트를 통과하지 못하면 이슈를 더 잘게 쪼개는 쪽으로 계획을 조정합니다.

## 12. 진화: 스스로 코딩 실력을 키운다

"진화"는 세 수준으로 나눌 수 있고, 이 중 1·2만 합니다.

| 수준                   | 무엇이 바뀌나                                                                       | 하는가                                                           |
| ---------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 1. 기억과 스킬 문서    | 규칙, 실패 사례, "이 저장소에서 X 하는 법" 같은 절차를 쌓고 비슷한 작업에서 꺼내 씀 | M4, M6                                                           |
| 2. 자기 작업 방식 수정 | 프롬프트, 작업 흐름, 도구 개선을 스스로 PR로 제안                                   | M7                                                               |
| 3. 모델 자체 학습      | 성공한 수정을 모아 로컬 모델을 추가 학습(LoRA)                                      | 하지 않음. 데이터 수십 건으로는 효과가 미미하고 망가질 위험이 큼 |

### 12.1 전제: 나아졌는지 측정한다

어려운 건 배우게 하는 것이 아니라, **실제로 나아졌는지 아는 것**입니다. 평가 없이 스스로 바뀌면 진화가 아니라 무작위로 흘러갑니다. 그래서 봇 자신의 작업 이력을 시험 문제로 씁니다.

```text
agent/evals/
└── cases/
    └── <이슈번호>.yml   # 작업 전 커밋, 이슈 본문, 지정 파일, 통과해야 할 테스트
```

- 머지된 봇 PR마다 문제 하나를 자동으로 추가합니다. 사람이 직접 처리한 작은 이슈도 넣을 수 있습니다.
- `uv run python -m src.app.agents.devbot eval`은 각 문제를 작업 전 커밋에서 다시 풀게 하고 **테스트 통과율**을 냅니다. 테스트는 정답 PR에 있던 것을 씁니다.
- 작업할수록 문제가 쌓이므로 평가 기준도 같이 자랍니다.
- 모델 응답에 무작위성이 있으므로 같은 문제를 3번 풀어 평균을 냅니다. 비교는 같은 모델끼리만 합니다.

### 12.2 1단계: 스킬 문서 (M6)

```text
agent/skills/
└── <스킬명>.md   # 언제 쓰는지, 절차, 이 저장소의 예시 파일, 주의점
```

- **만들기:** 회고 단계(4절 7단계)에서, 이번 작업이 반복될 만한 절차였으면 스킬 문서를 새로 쓰거나 기존 문서를 고칩니다. 예를 들면 "Pydantic 요청 모델에 검증 추가하기"나 "카드 계산기 테스트 쓰기" 같은 것입니다.
- **쓰기:** 구현 단계에서 이슈 내용과 가장 비슷한 스킬 문서 1~2개를 골라 모델 입력에 넣습니다. 처음에는 파일 이름과 첫 줄로 키워드 매칭을 합니다. 나중에 pypo 플랫폼의 검색 계층으로 바꿉니다.
- **검증:** 스킬 문서를 넣었을 때와 뺐을 때의 평가 점수를 비교합니다. 점수를 올리지 못하는 스킬 문서는 지웁니다.

### 12.3 2단계: 자기 개선 제안 (M7)

- 회고가 쌓이면 봇이 자기 작업 방식의 개선안을 냅니다. 대상은 프롬프트 파일(`agent/prompts/`), 스킬 문서, 구현 단계의 입력 선택 규칙입니다.
- **평가 점수가 기존보다 높을 때만** `bot-self` 라벨을 붙여 PR을 올립니다. PR 본문에는 개선 전후 점수와 문제별 결과를 넣습니다.
- 리뷰와 머지는 다른 PR과 똑같이 사람이 합니다.

### 12.4 넘지 않는 선

- **안전장치 코드와 평가 코드는 봇이 고칠 수 없습니다** (7절 수정 금지 경로). 이 선이 없으면 시험을 쉽게 바꿔서 점수를 올리는 쪽으로 진화합니다.
- 문제 세트에 문제를 추가하는 것은 정해진 코드만 하고, 봇의 LLM 단계는 관여하지 않습니다.
- 페르소나(`agent/persona.md`)는 사람만 바꿉니다.

## 13. 하지 않는 것

- 외부 저장소 기여
- 봇이 스스로 이슈를 만들거나 우선순위를 정하는 것. 계획은 사람이 씁니다
- 봇의 PR 자동 머지 (자기 개선 PR 포함)
- 모델 자체 학습 (12절 3단계)
- 유료 API. 0원 구성으로 지표가 나온 뒤 다시 판단합니다
- 범용 에이전트 프레임워크화 (STRATEGY 3단계에서)

## 14. 열린 결정

1. GitHub Models 무료 한도가 5절 방식(파일 1~3개 입력)에 충분한지. M5 전에 확인
2. 무인 운영을 Actions로 할지, 로컬 Mac 정기 실행으로 할지. 모델 성능은 로컬이 낫고, 안정성은 Actions가 낫습니다
3. 기억 변경을 작업 PR에 함께 넣을지, 별도 PR로 분리할지
