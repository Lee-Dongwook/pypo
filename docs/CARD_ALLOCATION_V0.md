# 카드 실적 배분 계산기: v0 프로브 명세

> 상태: 구현 착수. `docs/B2C_BENEFIT_GRAPH.md` 17절 결정에 따릅니다.
> 목적은 수익이 아니라 **계산 정확도와 재입력률** 확인입니다.

## 1. 한 줄 정의

**이번 달 남은 지출을 어느 카드에 몰아야 다음 달 혜택 구간을 넘는지, 넘기면 한도가 얼마나 느는지 알려주는 계산기.**

핵심은 추천보다 **거절**입니다. "3만 원 더 쓰면 2천 원 늘어납니다. 채우지 마세요"라고 말하는 서비스가 없습니다. 카드사 앱은 구조상 이 말을 할 수 없습니다.

## 2. 계산 규칙

### 2.1 입력

| 값           | 정의                            | 어디서 얻나                       |
| ------------ | ------------------------------- | --------------------------------- |
| `R` (카드별) | 이번 달 실적 인정 금액          | 카드사 앱의 "이번 달 실적" 표시값 |
| `P`          | 이번 달 남은 예상 지출          | 사용자 입력 1개                   |
| `T_i`, `C_i` | 구간별 기준 금액, 통합 할인한도 | 상품설명서 (큐레이션)             |

`R`은 총 사용액이 아니라 **실적 인정 금액**입니다. 세금·공과금·상품권·보험료·무이자할부·취소분은 빠집니다. 입력 화면에서 이 점을 먼저 안내하고, 사용자가 카드사 앱에 표시된 숫자를 그대로 넣게 합니다.

### 2.2 판정

```text
현재 구간 i   = R >= T_i 를 만족하는 가장 높은 구간 (없으면 한도 0)
다음 구간 j   = i + 1
남은 금액 g   = T_j − R
늘어나는 한도 = C_j − C_i
```

| 상황                                         | 판정             | 화면 문구                             |
| -------------------------------------------- | ---------------- | ------------------------------------- |
| `g > 0`, 한도 증가 > 0, 배분에 선택됨        | `fill`           | "N원 더 쓰면 한도가 M원 늘어납니다"   |
| `g > 0`, 한도 증가 > 0, 선택 안 됨, `g > P`  | `over_budget`    | "이번 달은 넘기지 마세요"             |
| `g > 0`, 한도 증가 > 0, 선택 안 됨, `g <= P` | `lower_priority` | "다른 카드가 더 이득입니다"           |
| `g > 0`, 한도 증가 = 0                       | `no_gain`        | "구간이 올라가도 한도는 그대로입니다" |
| 다음 구간 없음                               | `top_tier`       | "이미 최고 구간입니다"                |

### 2.3 배분

후보 카드 집합에서 다음을 푼다.

```text
maximize  Σ 늘어나는 한도
subject to Σ g <= P
```

카드가 5장 이하면 완전탐색으로 정확히 풀립니다. 동률이면 `g` 합이 작은 쪽을 고릅니다. 남은 돈은 사용자에게 남기는 게 맞기 때문입니다.

구현: `src/app/card/calculator.py`, 테스트: `tests/test_card_calculator.py`.

### 2.4 이 계산기가 하지 않는 것

- **실제 할인액 예측**: `늘어나는 한도`는 상한입니다. 그 카드로 실제 결제한 만큼만 할인됩니다. 화면에서도 "한도"라고 씁니다.
- **억지 지출 권유**: `P`는 어차피 쓸 돈입니다. `P`를 넘는 지출을 권하지 않습니다.
- 연회비 대비 손익, 카드 발급 추천, 업종별 추가 할인, 지난 거래 재배치.

### 추출 체크리스트

상품설명서에서 아래 네 가지만 뽑으면 계산이 됩니다. 나머지는 v1입니다.

1. 전월 실적 구간 금액 (보통 2~4개)
2. 구간별 통합 할인한도 (포인트 적립형이면 원 단위로 환산)
3. 실적 제외 항목
4. 조항 위치와 문서 기준일

주의할 것 두 가지.

- **포인트형 카드**: "1,000포인트"를 원으로 환산하는 기준(1P=1원 여부)을 명시해야 합니다. 환산 기준이 다르면 한도 비교가 틀립니다.
- **개정**: 상품설명서는 반기 단위로 바뀝니다. 기준일이 6개월 넘은 행은 화면에서 "오래된 약관"으로 표시하고, 갱신 전까지 신규 추천에서 뺍니다.

### 상태

| 상태            | 처리                                                      |
| --------------- | --------------------------------------------------------- |
| 카드 0장        | "카드를 먼저 등록해 주세요" (호스트 프로필에서 가져옴)    |
| 예산 0          | "남은 지출이 없으면 이번 달은 여기까지입니다"             |
| 후보 0          | "지금 구간을 넘길 카드가 없습니다. 다음 달에 다시 볼게요" |
| 전부 최고 구간  | "이미 최고 구간입니다. 추가 지출은 이득이 없습니다"       |
| 약관 6개월 경과 | 결과 대신 "약관 갱신 중" 표시                             |

### 문구 규칙

1. "받습니다" 대신 "한도가 늘어납니다". 실제 할인액이 아니기 때문입니다.
2. 숫자는 원 단위, 반올림 없음.
3. 모든 카드에 근거 조항과 기준일을 붙입니다. 접혀 있어도 존재해야 합니다.
4. "채우지 마세요"에 죄책감을 주는 표현을 쓰지 않습니다. 판단이 아니라 계산 결과입니다.

## 5. 측정

| 이벤트              | 시점                                             |
| ------------------- | ------------------------------------------------ |
| `card_probe_start`  | 진입                                             |
| `card_probe_submit` | 입력 완료                                        |
| `card_probe_result` | 결과 노출 (금액, 선택 카드 수, `over_budget` 수) |
| `card_probe_notify` | 다음 달 알림 신청                                |
| `card_probe_return` | 다음 달 재입력                                   |

| 지표                    | 기준     | 판정                                          |
| ----------------------- | -------- | --------------------------------------------- |
| 입력 완료율             | 80% 이상 | 미달이면 입력 문항 축소                       |
| 다음 달 재입력률        | 30% 이상 | 미달이면 카드 중단, 지원금으로 전환           |
| 예측 오차               | 1% 미만  | 명세서 대조 20건                              |
| `over_budget` 노출 비율 | 20% 이상 | 낮으면 "거절"이라는 차별점이 작동하지 않는 것 |

## 6. 일정

계산은 결정적이지만 **재입력률은 한 달을 기다려야** 나옵니다. 빌드 2주 + 관찰 4주, 판정은 6주째입니다.

| 주  | 결과물                                             |
| --- | -------------------------------------------------- |
| 1   | 카드 10개 큐레이션, 계산기 API, 테스트             |
| 2   | 화면 1장, 알림 신청, 배포 (월 20일 이전 배포 필수) |
| 3~5 | 사용자 50명, 결과 노출, 명세서 대조                |
| 6   | 재입력률 판정, 유지 또는 지원금 전환               |

20일 이후에 배포하면 다음 달 관찰 구간을 한 달 통째로 잃습니다.

## 7. 열린 결정

1. 카드 10개를 무엇으로 고를지. 사용자 보유 분포를 모르면 "국내 발급량 상위 10개"로 시작합니다.
2. 포인트형 카드를 v0에 넣을지. 환산 기준이 애매하면 원 단위 할인형만 넣는 편이 안전합니다.
3. 다음 달 알림을 앱 푸시로 할지, 문자로 할지. 문자는 이탈률이 낮지만 비용과 동의가 붙습니다.
4. 재입력률이 30% 근처일 때 판단. 25%면 유지할지 접을지 기준을 미리 정해야 합니다.

## 8. 실행 방법

```bash
# 백엔드
.venv/bin/python -m uvicorn main:app --port 8000

# 프론트엔드
pnpm install
pnpm dev            # http://localhost:3000
```

| 엔드포인트           | 역할                                  |
| -------------------- | ------------------------------------- |
| `GET /card/products` | 큐레이션된 카드 목록                  |
| `POST /card/plan`    | `{spends, planned_spend}` → 배분 결과 |

Next.js는 `/api/*` 요청을 `API_BASE_URL`(기본 `http://127.0.0.1:8000`)로 프록시합니다. 브라우저에서 API를 직접 호출할 때만 CORS가 필요합니다.

| 환경변수             | 기본값                          | 용도                    |
| -------------------- | ------------------------------- | ----------------------- |
| `CARD_CATALOG_PATH`  | `samples/card_products.v0.json` | 약관 큐레이션 파일 교체 |
| `API_BASE_URL`       | `http://127.0.0.1:8000`         | Next 프록시 대상        |
| `CORS_ALLOW_ORIGINS` | `http://localhost:3000,...`     | 허용 오리진             |

### 워크스페이스 구성

```text
apps/web            Next.js 15 App Router · TypeScript · Tailwind v4
                    Zustand(입력 상태) · TanStack Query(카탈로그·계산 요청)
packages/api-client API 타입과 호출 함수 (Pydantic 모델과 수동 동기화)
```

`src/app/card/api.py`의 응답 모델을 바꾸면 `packages/api-client/src/index.ts`도 같이 고쳐야 합니다. 아직 코드 생성은 없습니다.
